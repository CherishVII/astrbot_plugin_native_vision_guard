# 原生识图保护（Native Vision Guard）

> 一张已经失效的图片引用，不应该拖垮整条对话。

一个给 AstrBot 用的轻量插件。当你的主模型开启了「原生看图」（模型能力勾选了**图像**）时，它为这条链路加一条安全带：**某张图片取不到时，只丢那一张图，而不是让整条请求失败。**

---

## 一、它解决什么问题

### 现象

开启原生看图后，机器人某天开始持续报错，并且**同一个会话之后每次请求都失败**：

```
400 - {'error': {'message': '.messages[42]: Unsupported image_url format'}}
...
LLM 响应错误: All chat models failed: BadRequestError: Error code: 400 ...
```

### 原因

AstrBot 在把请求发给模型前，会把每个图片块解析成 `data:` URL。当某个图片引用**解析不出来**时
（最常见的情况：历史消息里引用的本地缓存文件已经被清理），`_transform_content_part`
会**把原始块原样返回**，于是那个裸路径被直接发给了模型服务商：

```python
# astrbot/core/provider/sources/openai_source.py（未修复版本）
if not image_data:
    logger.warning("图片预处理结果为空，将忽略。")   # 日志说"将忽略"
    return None

...
return resolved_part or part      # 实际上却把原始块原样发了出去
```

模型服务商只接受 `data:` URL、公网 `http(s)` 链接或 Files API 的 `file_id`，
收到一个本地路径就回 `Unsupported image_url format`，**整条请求被拒绝**。

更麻烦的是：这张坏图留在会话上下文里，**之后该会话的每一次请求都会继续失败**——
不是偶发一次，而是持续性的。

### 本插件怎么做

在插件加载时，用运行时替换（monkeypatch）把 `_transform_content_part` 换成安全版本：

- 解析**失败**的图片 → 降级为 `[Image unavailable]` 文本块，请求照常发出；
- 解析**成功**的图片、文本块、音频块 → **一律委托原实现**，行为完全不变。

这与 AstrBot 自己对"当前消息图片"的既有降级行为是一致的（`image_input.py` 在图片取不到时
也会标注 `skipped: image unavailable` 并继续发送），本插件只是把**历史上下文**这条路径补齐。

## 二、什么时候需要它

| 你的情况 | 是否需要 |
|---|---|
| 主模型「模型能力」勾选了**图像**（原生看图） | ✅ 需要 |
| 主模型只勾了文本，图片走插件/工具的按需识别 | ❌ 不需要 |
| 你在用 AngelHeart 这类会往历史里放图片引用的插件 | ✅ 强烈建议 |

## 三、安装

### 方式一：插件市场

在 AstrBot WebUI → 插件 → 插件市场，搜索本插件名安装。

### 方式二：从文件安装

1. 下载本插件的 zip；
2. WebUI → 插件 → 安装插件 → 从文件安装 → 选择 zip；
3. 安装后确认插件处于**已打开**状态。

### 安装后必做的一步

把主模型提供商的「模型能力」勾上**图像**（否则原生看图不会启用）：

```
模型提供商 → 你的提供商 → 模型能力：☑ 文本  ☑ 图像  ☐ 音频  ☑ 工具使用
```

> 「工具使用」建议保留，取消它会让 AstrBot 清空全部工具。

保存后重启一次 AstrBot。

## 四、验证是否生效

**1. 看启动日志**，应出现：

```
[native_vision_guard] ACTIVE - patched <类名>._transform_content_part
```

**2. 随时自查**：在任意会话发送指令

```
/vision_guard
```

应回复 `native_vision_guard: ACTIVE - patched ...`。

**3. 发一张图**：日志里应是**直接回复**，且不再出现
`Agent 使用工具: ['angel_describe_image']`、`图片预处理结果为空，将忽略。`

## 五、保险机制

本插件替换的是 AstrBot 的内部方法，因此内置了三重保险，避免"帮倒忙"：

| 情况 | 插件行为 |
|---|---|
| **上游自己修好了**这个方法 | 检测到问题代码已不存在 → **拒绝覆盖**，日志提示 `NOT ACTIVE - upstream no longer contains the buggy fallback` |
| 目标类 / 方法被重命名 | 明确告警并保持原样，**绝不静默失效** |
| 插件被重复初始化 | 幂等，不会叠加多层补丁 |

也就是说：**AstrBot 升级后你什么都不用做。** 上游修好了它会自动让位；没修好它继续生效。

## 六、兼容性与实测

- **实测版本**：AstrBot `v4.28.2`（含 shim 插件安装、原生看图、坏引用降级全链路验证）。
- **实现方式**：仅依赖 `openai_source` 中 `_transform_content_part` 这一个方法名。
  这是本插件唯一相对"脆弱"的地方，因此配套了上面的检测与告警。
- **平台无关**：工作在模型提供商层，与消息平台适配器无关。

## 七、卸载与回滚

> ⚠️ **顺序很重要**：先取消「模型能力」里的**图像**勾选并保存，**再**禁用或删除本插件。
> 反过来的话，会出现"声明支持图像但没有安全带"的窗口期，此时遇到失效图片引用会退回 400 报错。

卸载方式：WebUI → 插件 → 禁用或删除本插件 → 重启。
插件不修改任何源码文件，删除后无残留。

## 八、常见问题

**Q：日志显示 `NOT ACTIVE` 怎么办？**
A：两种情况——① `upstream no longer contains the buggy fallback`：说明 AstrBot 已自行修复，你不再需要本插件，可放心卸载；② 找不到目标类/方法：说明 AstrBot 内部结构变了，请提 Issue 附上该行日志。

**Q：它会改变我正常的图片识别行为吗？**
A：不会。解析成功的图片走的是原实现，本插件只在"解析失败"这一条路径上介入。

**Q：会不会影响其他插件？**
A：不会。它只替换一个方法，且对该方法的非图片分支完全委托原实现。

**Q：上游修好后我还需要留着它吗？**
A：不需要。它检测到上游修复后会自动不生效，你可以随时卸载。
